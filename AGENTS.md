# AGENTS.md

Инструкции для работы в Budget — pnpm-монорепозитории учёта доходов и расходов: React/Vite frontend, Fastify backend, Prisma/SQLite и TypeSpec-контракты с Orval-клиентом.

## Общение и язык

- Общайся с пользователем по-русски, кратко: результат, затем обоснование.
- Комментарии в коде — по-русски, по [правилу необходимости](#комментарии-в-коде). Логи, идентификаторы и имена файлов — по-английски.
- Если неоднозначность мешает корректному или безопасному результату, уточни её до изменения файлов. Для значимого выбора предложи 2–3 варианта с плюсами, минусами и рекомендацией.

## Рабочий процесс

1. Определи цель, ожидаемый результат, границы изменений, риски и способ проверки.
2. Перед проектированием или реализацией прочитай `projects/solution.md`, `projects/tasks_list.md`, относящиеся к работе файлы задач и `projects/backlog.md`, если они существуют. Для терминов и архитектурных решений прочитай соответствующие `GLOSSARY.md` и ADR, если они есть; `GLOSSARY-MAP.md` указывает на глоссарии отдельных контекстов.
3. Для новых функций, изменений и багов используй установленный `task-intake`: согласуй решение до записи задач и изменения production-кода. Для автономной реализации уже описанных задач по явному запросу используй `autonomous-tasks`.
4. Смотритель ведёт статусы одновременно в файле задачи и `projects/tasks_list.md`; субагенты возвращают ему результаты для обновления статусов. Известные проблемы вне текущего объёма смотритель записывает в `projects/backlog.md`.
5. Выполни проверки затронутых областей. Работа завершена, когда выполнены критерии приёмки, проверки прошли или блокер явно описан, статусы обновлены, а пользователь получил результат и существенные ограничения.

## Команда агентов

- В основном диалоге выполняй роль смотрителя: перед работой прочитай [.agents/supervisor/instructions.md](.agents/supervisor/instructions.md) и следуй указанному там процессу. Субагент читает инструкции назначенной ему роли из `.agents/<role>/instructions.md`.
- Смотритель координирует работу и передаёт результаты: `spec-writer` составляет ТЗ, `developer` реализует, `tester` проверяет поведение, отдельный `reviewer` проверяет архитектуру и соответствие ТЗ. Границы и передача результатов описаны в [.agents/supervisor/workflow.md](.agents/supervisor/workflow.md); модели — в [.agents/supervisor/models.md](.agents/supervisor/models.md).
- Результаты ролей сохраняй как Markdown с YAML по [.agents/supervisor/artifacts.md](.agents/supervisor/artifacts.md); смотритель проверяет их через `pnpm agents:check` и собирает сводку через `pnpm agents:summary`.
- Материалы ролей находятся в собственных каталогах `.agents/`, память и общий список — в `projects/`, документы конкретной работы — в `projects/tasks/<work>/`. В `.codex/` хранятся настройки подключения Codex и указатели на проектные материалы.
- Пути `.codex/solution.md`, `.codex/tasks/`, `.codex/backlog.md` и `.codex/sessions/` в установленных скиллах адаптируй к `projects/solution.md`, `projects/tasks/<work>/work-items/`, `projects/backlog.md` и `projects/tasks/<work>/sessions/`. Проектный процесс распределяет тесты агенту `tester`, координацию и принятие результата — смотрителю. Лимиты повторных проверок и полномочия бери из текущего запроса и `.agents/supervisor/workflow.md`.

## Скиллы

Локальные скиллы находятся в `.agents/skills/<name>/SKILL.md`. Перед применением прочитай соответствующий файл и только нужные ему дополнительные материалы. Сообщи пользователю о первом применении скилла. Учитывай `disable-model-invocation: true`: такие скиллы запускаются по явному запросу пользователя или вызову другим скиллом.

Общую библиотеку сохраняй одним экземпляром; выбор по ролям и подключение будущих уникальных скиллов описаны в [.agents/supervisor/skills.md](.agents/supervisor/skills.md). Карта применения находится в `instructions.md` каждой роли и сохраняет её границы владения и делегирования.

## Архитектурные ограничения

### Frontend

- Следуй FEOD: `app → pages → modules → common`. Публичный интерфейс каждого модуля, включая вложенные, экспортируется из `index.ts`; внешний код импортирует модуль через него.
- `app/routes` содержит тонкие TanStack Router adapters: `createFileRoute`, route hooks и передачу данных/действий в страницы. `pages` компонуют экран и состояние маршрута; бизнес-логика принадлежит `modules`.
- Состояние маршрута, search и навигации держи в adapters или страницах. Новые страницы получают route data/actions через параметры; существующие импорты `pages → app/routes` — legacy-исключение.
- В модулях размещай UI в `ui/`, типы, схемы и hooks — в `model/`. Legacy hooks в корне переноси в `model/`, когда затрагиваешь их модуль.
- Разделяй UI по видимым блокам, модель — по сценариям, endpoints, adapters, схемам и типам. Для внутреннего workflow рассматривай вложенный модуль. Перед коммитом проверь, что дерево файлов объясняет устройство функции.
- `common` — общая инфраструктура: прямые импорты конкретных файлов разрешены, `index.ts` не обязателен.
- Данные для render вычисляй во время render, действия обрабатывай в event handlers или query hooks. `useEffect` используй для кода, необходимого из-за показа компонента пользователю; вычисление render-данных и синхронизацию локального state из props выполняй без effects.
- Для цветов используй существующие семантические CSS-переменные; проверяй затронутый UI в светлой и тёмной темах.
- Новые страницы и модули создавай через frontend `scaffold`; варианты и параметры описаны в development guide и CLI. `--parent` задаётся относительно `src/modules`, вложенные модули находятся в `modules/<parent>/modules/<child>`.

### Backend и данные

- Доменное поведение держи в соответствующем `apps/server/src/domains/`; общую инфраструктуру — в plugins. Используй существующие aliases из `apps/server/package.json`.
- Prisma-схема и миграции находятся в `apps/server/prisma/`; клиент внедряется через `apps/server/src/plugins/prisma/prismaPlugin.ts`.
- Токен удостоверяет только пользователя. Счёт-зависимые запросы передают `accountId` явно в path (`/accounts/{accountId}/...`); доступ проверяется владением или членством `AccountUser` (403), данные ограничиваются счётом запроса. Категории и подкатегории используют soft delete через `deletedAt`; учитывай исторические операции.

### API и генерация

HTTP-контракт меняй сначала в `packages/api-contracts/typespec/` (`main.tsp` — entry point), затем регенерируй:

1. `pnpm --filter @budget/server typespec` — OpenAPI и серверные схемы.
2. `pnpm --filter @budget/frontend api:generate` — Orval-клиент.
3. Обнови handlers и frontend-модули, затем проверь типы и затронутые сценарии.

После изменения Prisma-схемы обнови миграции и выполни `pnpm --filter @budget/server prisma:generate`.

Generated-файлы обновляй только генераторами; вручную их не редактируй:

- `apps/frontend/src/common/api/generate/`
- `apps/frontend/src/app/routes/routeTree.gen.ts`
- `apps/server/generated/`
- `packages/api-contracts/generated/`

## Комментарии в коде

- Сначала выражай смысл именами, типами и структурой кода. Комментарий добавляй только если без него теряется важная причина решения или ограничение, которое нельзя понять из кода и незнание которого может привести к ошибочной правке. Обычной реализации отдельное пояснение не требуется.
- Объясняй, почему выбран этот вариант: внешнее ограничение, неочевидный компромисс, условие совместимости или последствие кажущегося упрощения. Пересказ действий, параметры и порядок вызовов, уже видимые в коде, комментария не требуют. В тестах действует тот же критерий: поясняй неочевидную причину сценария или устройства стенда.
- Пиши кратко, обычно одной строкой; дополнительный текст нужен только для сохранения существенного основания. Для развёрнутого архитектурного решения используй проектную документацию и при необходимости ссылку на неё. Комментарий не заменяет понятное имя, небольшой модуль или проверку инварианта тестом.
- Указывай только подтверждённую причину. При чтении комментарий считай объяснением намерения автора, которое нужно сверить с кодом и актуальными требованиями. Сам по себе он не доказывает необходимость ограничения. Неустановленное основание передавай как вопрос, а не придумывай оправдание реализации.
- При изменении связанного кода проверь актуальность комментариев в пределах назначенного владения: устаревшую причину исправь или удали, избыточный пересказ убери. Незатронутые комментарии массово не очищай. Обязательные лицензии, директивы инструментов и generated-комментарии сохраняй по их назначению и правилам генерации.

## Код и проверка

- Следуй существующим TypeScript, ESLint, Prettier и import sorting настройкам. Новые файлы и папки называй в kebab-case, кроме требований генератора или framework.
- При изменении существующего handwritten-файла с camelCase-именем переименуй его в kebab-case в рамках той же задачи: `useTransactions.ts` → `use-transactions.ts`, `useTransactions.test.ts` → `use-transactions.test.ts`. Обнови импорты, реэкспорты, пути моков, конфигурацию и ссылки, затронутые переименованием; проверь отсутствие старого пути и выполни проверки затронутой области. Идентификаторы внутри файла сохраняют принятый стиль. Имена, заданные framework или генератором, следуют их правилам; generated-файлы меняются только генераторами. Для нужных изменений вне назначенного владения supervisor согласует последовательность с владельцами. Незатронутые файлы не переименовывай массово.
- Новые и изменяемые unit-тесты и локальные integration-тесты приложения размещай в `tests/` внутри каталога проверяемого кода: `model/use-transactions.ts` → `model/tests/use-transactions.test.ts`, `helpers/balance.ts` → `helpers/tests/balance.test.ts`. Существующий тест при его правке переноси туда же, сохраняя назначение и суффикс `.test.ts`/`.test.tsx`; файл, уже находящийся в нужной `tests/`, повторно не вкладывай в `tests/tests/`. Обнови зависимые импорты, моки, fixtures, конфигурацию и ссылки, затем проверь перенесённые тесты. Незатронутые тесты остаются на местах до их изменения. E2E храни отдельно в `e2e/` по пользовательским сценариям; конфигурационные каталоги тестов самого harness этим правилом не меняются.
- Предпочитай существующие helpers и простые абстракции в соответствующем домене. Связанные типы выводи из исходного типа или tuple: indexed access, `typeof VALUES[number]`, `Record<DomainType, ...>`.
- В handwritten-коде используй type guards, схемы, типизированные константы и узкие interfaces вместо `value as Type`. `as const` разрешён. Неизбежный non-const assertion требует явного согласия пользователя и объяснения причины.
- Для бага сначала найди первопричину: воспроизведение, по возможности падающий тест, одна гипотеза за раз. После повторных неудачных попыток сообщи установленные факты и оставшуюся неопределённость.
- Первопричину устраняй в месте её возникновения, а не компенсируй логикой в соседнем слое: дефект контракта или поведения backend не закрывается флагами и блокировками на frontend. Если причина вне текущего объёма или владения, предложи пользователю исправить её в месте возникновения и расширь объём либо заведи отдельную задачу; субагент передаёт предложение supervisor. Компенсация в своём слое — только явно согласованное временное решение с записью проблемы в `projects/backlog.md` и задачей на устранение причины.
- Сохраняй корректные тесты; исправляй реализацию вместо ослабления проверок. Выбирай проверки по изменённому поведению, а команды — по scripts пакета и критериям задачи.
- Для frontend обычно нужны `ts:check`, `lint` и `test`; для server — `build` и `lint`. Для изменённых пользовательских сценариев используй frontend `e2e` или браузерную проверку. Playwright-конфигурация поднимает frontend; требования backend уточняй по выбранному тесту.
- Для изменений только документации проверяй ссылки, команды и diff; тесты приложения не требуются.

## Артефакты и коммиты

- Пользовательские планы и обзоры отделяй от спецификаций, планов исполнения и отчётов агентов: выбирай аудиторию и путь по [правилам хранения](.agents/supervisor/storage.md#аудитория-и-назначение-документа); пользователю сначала показывай материал из `projects/tasks/<work>/user.md`.
- Публичную документацию проекта размещай в `docs/`. Все новые рабочие материалы агентов сохраняй в `projects/` по [правилам хранения](.agents/supervisor/storage.md): ТЗ, задачи, планы, исследования, черновики, отчёты, логи, скриншоты и материалы воспроизведения. `docs/_drafts/` — архив для чтения; пополнение и изменение архива требуют прямого указания пользователя.
- Пути рабочих документов и вручную выбираемые output-пути из любых скиллов адаптируй к этим правилам, включая `docs/_drafts/`, `docs/plans/`, `docs/superpowers/` и `.codex/`. Явно заданный пользователем путь имеет приоритет.
- `projects/`, `.codex/`, `.claude/`, `.playwright-mcp/`, `.playwright-cli/`, `.mcp.json` и browser output сохраняй локально. Инструкции ролей в `.agents/<role>/` и общие скиллы в `.agents/skills/` — конфигурация проекта. Путь скилла для рабочего документа адаптируй к этим правилам; постоянные глоссарии и ADR — проектная документация.
- Коммить только относящиеся к изменению source, tests, configuration, намеренно отслеживаемые generated-файлы и публичную документацию. Существующие чужие изменения сохраняй.
- Используй короткие Conventional Commits, один логический change на коммит, без Claude/Codex authorship trailers. Push выполняй только по явному указанию пользователя в текущей сессии.
