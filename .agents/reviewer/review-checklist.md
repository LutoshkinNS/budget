# Чеклист review

Проверяй затронутые области; для неприменимых укажи `н/п` с причиной. Основа review — задача, согласованная spec и срез из поручения.

- [ ] **Версия и границы.** Baseline неизменяема, способ сравнения известен, task-scoped diff полон, финальный snapshot совпадает с кодом и evidence. Посторонние изменения отделены; связанный код прочитан для проверки влияния.
- [ ] **Spec.** Каждый AC сопоставлен с реализацией; успешные, ошибочные и граничные случаи соответствуют согласованным контрактам. Scope/non-goals соблюдены, нужные зависимости доступны.
- [ ] **Архитектура и сопровождение.** Соблюдены документированные границы и публичные интерфейсы, доменная логика находится у своего владельца; изменения не создают доказуемого дублирования, циклов или избыточной сложности. Предложения обосновывай конкретным последствием.
- [ ] **Комментарии.** Добавленные и затронутые комментарии соответствуют [правилу необходимости](../../AGENTS.md#комментарии-в-коде); проверь их основания независимо от текста. Замечание обоснуй конкретным лишним пояснением, утраченной причиной или вводящим в заблуждение утверждением.
- [ ] **Первопричина.** Изменение устраняет первопричину в месте её возникновения. Компенсацию дефекта из другого слоя или владения (например, frontend-флаг против гонки из cookie-контракта backend) отмечай finding'ом с направлением исправления в месте причины, если она не согласована пользователем как временное решение с записью в backlog.
- [ ] **Async/context.** Для применимых сценариев рассмотри lifetime контекста, переходы и перекрывающиеся действия независимо от тестовых примеров; попытайся построить правдоподобный контрпример и укажи в отчёте рассмотренные сценарии и вывод, в том числе если дефектов нет. Отдельно оцени, подтверждают ли тесты эти инварианты на соответствующих границах. Для простой синхронной правки укажи `н/п` с причиной.
- [ ] **Frontend / FEOD.** При изменении frontend проверь `app → pages → modules → common`, импорты через публичные интерфейсы, владение route state, размещение модели/UI, effects и семантические цвета по frontend-документации. Evidence tester по UI относится к обеим темам и финальному срезу.
- [ ] **Backend / API / данные.** При изменении соответствующей области проверь доменные границы, account scope и soft delete; контракт TypeSpec, совместимость handlers/client и генерацию; Prisma-схему, миграции, сохранность исторических данных и генерацию клиента. Generated-файлы сопоставь с источниками и evidence генераторов.
- [ ] **Проверки и исправления.** Evidence tester покрывает AC и регрессии на актуальном срезе; неподтверждённое выполнение не считай успешным. После исправлений developer повторно проверь touched findings и влияние diff; регрессии направь tester через supervisor.
- [ ] **Безопасность по запросу.** Явный запрос security review определяет объём дополнительной проверки и применение `security-best-practices`; иначе этот пункт — `н/п`.

## Findings и результат

Для каждого finding укажи ID, severity, ось `Spec` или `Standards`, точный `path:line`, нарушенный AC/правило, условия возникновения, фактическое и ожидаемое поведение, влияние, evidence и проверяемое направление исправления. Доказательство может быть цепочкой по коду; предположения обозначай как вопросы. Стилевые предпочтения и необоснованные рефакторинги findings не образуют. Прежний дефект вне diff передай supervisor как предложение backlog, не приписывай текущей реализации.

Severity: `P0` — критическая проблема, требующая немедленной остановки; `P1` — высокий ущерб или сломанный основной сценарий; `P2` — существенный дефект в определённых условиях; `P3` — локальный дефект с малым влиянием. Оценивай по подтверждённым последствиям.

- `pass` — применимые проверки завершены, открытых подтверждённых дефектов нет.
- `fail` — есть подтверждённый дефект, требующий исправления.
- `blocked` — review нельзя завершить из-за отсутствующих входных данных, evidence или актуального среза; укажи конкретное условие продолжения.

Итог сворачивается из checks по общему протоколу: `fail` имеет приоритет над `blocked`, затем `pass`. Непроверенные области и устаревшие выводы перечисляй явно; pass reviewer не подменяет результат tester или публикацию статуса supervisor.
