# Качество тестов Vitest

Применяй этот чеклист, когда пишешь, меняешь или проверяешь автоматизированные тесты на Vitest. Ожидаемое поведение бери из согласованного ТЗ, а исходники изучай, чтобы знать реальные API, типы и зависимости. Основа рекомендаций — [Writing Tests with AI](https://main.vitest.dev/guide/learn/writing-tests-with-ai); учитывай API установленной версии.

## Подготовь контекст

- Прочитай функцию или компонент целиком вместе с импортами и типами, зависимости, близкие тесты и конфигурацию Vitest. Проверь package script, environment и setupFiles, если они заданы.
- Следуй стилю соседних тестов и контракту ТЗ. Имена кратко описывают проверяемое поведение.

## Проверь поведение

- Свяжи тесты с критериями ТЗ. Добавь релевантные успешные, ошибочные и граничные случаи: например пустые данные, границу диапазона или отказ зависимости. Не создавай искусственные случаи без основания.
- Проверяй наблюдаемый результат понятным assertion: возвращённые данные, UI, ошибку или публичный эффект. Ожидаемое значение должно быть независимым от реализации. Проверка только «не упало», `toBeDefined()` для любого результата или мок самого assertion не подтверждают критерий.
- Оцени чувствительность теста: изменится ли он, если требуемое поведение сломается? Избегай привязки к внутренним деталям, если внешний контракт можно проверить напрямую. Моки вызовов полезны, когда эти вызовы сами составляют контракт.

## Проверь надёжность и запуск

- Мокируй границы системы и непредсказуемые зависимости; для контролируемых модулей предпочитай реальное поведение. Обоснуй необходимый мок и не проверяй его вызовы вместо результата.
- Async-код ожидай через `await`; ошибки проверяй через `.rejects` или другие подходящие асинхронные assertions. Не оставляй фоновые операции между тестами.
- Используй `vi.*` и импорты Vitest, соответствующие конфигурации. При мокировании модулей предпочитай типобезопасный `vi.mock(import(...))`, если он поддерживается установленной версией и корректен для пути. Очищай или восстанавливай изменённые моки, таймеры и окружение. Учитывай `clearMocks` / `restoreMocks` из конфигурации, но не полагайся на них для очистки вручную созданного состояния.
- Параметризуй повторяющиеся случаи по смыслу. Snapshot применяй для устойчивого содержимого, которое важно целиком; проверяй, что он не скрывает нужный assertion.
- Запусти точный тест и подходящую проверку пакета командой без watch из `package.json`. После запуска просмотри тесты и результат: сборка без ошибок не доказывает, что проверки содержательны.

Общие принципы тестов и выбора моков смотри в [tdd/tests.md](../skills/tdd/tests.md) и [tdd/mocking.md](../skills/tdd/mocking.md); это справка по качеству, а не требование запускать TDD для каждой задачи.
