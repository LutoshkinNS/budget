# Готовность задачи к выдаче

Spec-writer использует чеклист при подготовке задачи; supervisor проверяет полноту перед выдачей worker и передаёт результаты между ролями. Независимые review и тестирование выполняют reviewer и tester. Готовность — условие выдачи, а не новый статус: сохраняются `todo`, `in-progress`, `done`, `blocked`. Статусы в задаче и общем индексе ведёт supervisor.

- [ ] **Контекст проверен.** Указаны прочитанные пути и релевантные символы, текущее поведение и версия изученного кода: HEAD и относящиеся к задаче незакоммиченные изменения. Новые пути явно обозначены. При смене HEAD или затронутого diff перед выдачей supervisor обеспечивает перепроверку зависимых фактов.
- [ ] **Результат определён.** Цель и наблюдаемое поведение связаны с ID критериев ТЗ; есть основание согласования, scope и non-goals. Существенные ограничения и риски названы.
- [ ] **Владение разделено.** Конкретные разрешённые source/config/generated-пути отделены от tests/fixtures, у каждой области есть предлагаемая роль. Генерируемые файлы связаны с источником и генератором. Совпадающее владение требует последовательной работы, назначенной supervisor.
- [ ] **Контракты однозначны.** Для затронутой области описаны входы, выходы, ошибки и инварианты; есть конкретные примеры успешного, ошибочного и граничного сценариев с ожидаемым результатом. UI, API, БД и миграции описываются только при их изменении.
- [ ] **Зависимости проверяемы.** Для каждой зависимости указаны задача/путь, необходимый результат и способ убедиться, что он доступен. До выдачи supervisor проверяет эти условия; одного статуса `done` недостаточно.
- [ ] **Шаги исполнимы.** Есть порядок действий с промежуточными результатами. Алгоритм задаётся там, где он часть согласованного решения; локальные детали реализации выбирает developer в выданных границах. Большую или неоднозначную работу разделяют на проверяемые задачи до выдачи.
- [ ] **Каждый AC проверяется.** Критерий связан с проверкой и её владельцем; указаны точная команда или ручной сценарий, cwd, env/подготовка данных, ожидаемый результат. Команды сверены с текущими scripts/config; для общей проверки явно названы покрываемые AC.
- [ ] **Review определён.** Есть задача и согласованная spec, проверяемая граница diff и неизменяемая база для итогового review; supervisor назначает reviewer финальный snapshot. Для сложных изменений можно назначить предварительные notes по design/task в drafts; они не являются итоговой приёмкой. Процесс reviewer описан в [инструкциях роли](../reviewer/instructions.md).
- [ ] **Блокирующие вопросы разрешены.** Supervisor разрешил вопросы требований, владения и окружения; решения о пользовательском поведении подтверждены пользователем. Обнаруженный пробел возвращается supervisor до выдачи worker, без домысливания требований.

Масштаб описания соразмерен задаче: краткого пункта или ссылки на точный раздел ТЗ достаточно. Для неприменимых полей укажи `н/п` с причиной; в тривиальной задаче не нужны искусственные API/БД, сценарии ошибок или подробный алгоритм. Ссылки должны давать worker конкретный ответ, а не требовать заново проектировать решение.
