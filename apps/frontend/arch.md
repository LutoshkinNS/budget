# FEOD — Fractal Entity Oriental Design

> Архитектурный подход к организации фронтенд-приложений от команды Sportmaster Lab.  
> Источник: [Habr — От хаоса к структуре](https://habr.com/ru/companies/sportmaster_lab/articles/972410/)

---

## Что такое FEOD?

FEOD — это подход к структурированию фронтенд-проектов, который объединяет лучшее из существующих практик:

| Источник | Что взято |
|---|---|
| **Atomic Design** | Гранулярное разделение элементов |
| **Feature-Sliced Design (FSD)** | Правила слоёв и импортов |
| **Модульный подход** | Гибкость в формировании блоков |
| **Гексагональная архитектура** | Изоляция модулей и публичный API |

Главная цель — убрать перегруженную терминологию и споры на code review, дав разработчикам чёткие критерии: **что и куда класть**.

---

## Три ключевых концепции

### 1. Модульность
Проект делится на логические блоки с чёткими границами ответственности. Каждый модуль изолирован и общается с остальными только через публичный API.

### 2. Фрактальность
Модуль может содержать подмодули, те — свои подмодули, и так до любой глубины. Структура повторяет себя на каждом уровне — архитектура масштабируется без потери предсказуемости.

### 3. Сущности
Каждый элемент кодовой базы имеет роль и назначение. Не просто «файл в папке», а осознанная часть системы.

## Слои FEOD

```
App
 └── Pages
      └── Modules  ←─── фрактально вложенные подмодули
           └── Common
                └── Global (опционально)
```

### Global _(опциональный)_
- Shim-ы библиотек, глобальные компоненты (например, во Vue), метаданные роутера
- **Никого не импортирует** — доступен везде без явных импортов
- Не путать с Common: Global «растворяется» в проекте

### Common
- Переиспользуемые утилиты и UI-компоненты **без бизнес-логики**
- Может импортироваться откуда угодно
- Common-сущности **не связаны между собой**
- ⚠️ **Без индексных файлов** — они ломают tree-shaking и превращают Common в склад

### Modules
- Бизнес-логика, крупные связки сущностей, «скоупы знаний»
- Модули могут использовать другие модули, но только через их публичный API
- **Нельзя импортировать из Common** — только в обратную сторону
- Поддерживают **фрактальную вложенность** (подмодули → под-подмодули)

### Pages
- Собирают готовые страницы из модулей
- URL страницы повторяет путь к её файлу
- Могут импортировать из Modules и Common, но **не наоборот**
- App не импортируется напрямую — данные передаются через пропсы или инверсию контроля
- Поддерживают приватные модули (компоненты только для одной страницы)

### App
- Конфиги, роутер, layout, точка запуска приложения
- Может импортировать кого угодно
- **Никто не импортирует из App**
- При необходимости передать данные наружу — используется инверсия контроля

## Правила импортов

```
Global   →  никуда
Common   →  Common
Modules  →  Common, другие Modules (только index.ts)
Pages    →  Modules, Common
App      →  все слои
```

**Главное правило:** импорт из модуля — только через его `index.ts` (публичный API).  
Прямой доступ к внутренним файлам модуля — нарушение архитектуры.

---

## Фрактальность модулей

```
modules/
└── user/
    ├── index.ts          ← публичный API
    ├── profile/
    │   ├── index.ts      ← публичный API подмодуля
    │   └── avatar/
    │       ├── index.ts  ← публичный API под-подмодуля
    │       └── ...
    └── settings/
        ├── index.ts
        └── ...
```

**Когда создавать подмодуль:**
- Модуль стал слишком большим
- Нужно разделить ответственность внутри команды
- Появилась необходимость документировать отдельную часть

**Плюсы вложенности:**
- Чёткие границы — связи не растут экспоненциально
- Изолированные модули проще тестировать
- Каждый подмодуль можно сопроводить документацией

---

## Common — когда он перестаёт быть Common

Если в Common появляются несколько связанных между собой сущностей — это сигнал вынести их в отдельный модуль.

```
// Было в Common — норм:
tooltip.ts

// Стало в Common — пора в модуль:
tooltip.ts
tooltip-manager.ts
useTooltip.ts
TooltipProvider.ts
```

Полезный мысленный тест: если хочется «спрятать» несколько сущностей и оформить их в набор — это уже модуль, а не Common.

---

## Переход на FEOD: 4 шага

1. **Выделить App** — зафиксировать точку запуска и конфиги
2. **Привести к порядку Pages / Views** — имена файлов по URL
3. **Разбить логику по Modules** — ориентироваться на зоны ответственности команды
4. **Остаток — в Common** — всё без бизнес-логики уходит сюда

## Расширения для продвинутых проектов

### SSR
Вместо единого App выделяется слой **Server** с двумя файлами:
- `EntryServer.ts`
- `EntryClient.ts`

### Dependency Injection
Вместо прямых кросс-модульных связей — явные зависимости через DI (инструмент SDI). Делает архитектуру управляемой при росте проекта.

### DDD-интеграция
Внутри модулей можно выделить `Entities` и `Adapters` для команд, привыкших к Domain-Driven Design.

## Сравнение с другими подходами

| Подход | Сильные стороны | Слабые стороны |
|---|---|---|
| **Atomic Design** | Понятная визуальная иерархия | Не отвечает на вопросы бизнес-логики |
| **FSD** | Строгие правила, чёткие слои | Тяжёлая ментальная модель, много споров |
| **Модульный** | Гибкость | Нет единого стандарта, хаос связей |
| **FEOD** | Баланс гибкости и правил, низкий порог входа | Молодой подход, меньше community |

## Итог

FEOD даёт:
- **Разработчикам** — единый язык, прозрачные правила, меньше споров на ревью
- **Командам** — быстрый онбординг, предсказуемое масштабирование
- **Бизнесу** — управляемая стоимость поддержки и роста проекта
