# Архитектура backend

Соглашение для нового и изменяемого кода `apps/server`. Пример полной структуры — модуль [categories](../src/domains/categories/routes.ts). Общий обзор системы находится в [architecture.md](../../../docs/architecture.md), команды настройки и генерации — в [development.md](../../../docs/development.md).

`accounts` и `auth` уже частично разделены на маршруты, обработчики и repositories, но некоторые handlers обращаются к Prisma напрямую. `transactions` и `subcategories` также содержат совмещённую реализацию. Это существующие отклонения: переносить их постепенно в рамках относящихся к ним задач.

## Устройство сервера

- [main.ts](../src/main.ts) подключает доменные маршруты и запускает сервер.
- [app-init.ts](../src/app-init.ts) создаёт Fastify и подключает инфраструктурные plugins: окружение, cookies, авторизацию, Prisma и обработку ошибок.
- `src/domains/<domain>/` содержит сценарии соответствующей предметной области.
- `src/plugins/` содержит общую инфраструктуру. Правила категорий, операций или счетов туда не переносятся.

Путь запроса:

```text
HTTP-запрос
  → Fastify hooks и проверка схем
  → handler: сценарий и HTTP-ответ
  → repository: чтение и запись
  → Prisma → SQLite

handler → чистые helpers
routes и types → TypeSpec-схемы
```

## Структура доменного модуля

```text
categories/
  routes.ts
  types/
    category.ts
  schemas/
    category-list-query.ts
  handlers/
    list.handler.ts
    get.handler.ts
    create.handler.ts
    update.handler.ts
    delete.handler.ts
    validate-icon-key.hook.ts
    errors.ts
  repositories/
    categories.repository.ts
  helpers/
    category-name.ts
    category-icon.ts
    category-serializer.ts
    category-usage.ts
  tests/
    categories.test.ts
    category-usage.test.ts
```

Новые файлы называются в kebab-case. Суффиксы `.handler.ts`, `.hook.ts` и `.repository.ts` обозначают назначение файла. Типы размещаются отдельно в `types/`, runtime-схемы — в `schemas/`, чистые функции — в `helpers/`. Имена внутри каталогов должны объяснять сценарий или ответственность; один общий `utils.ts` для несвязанных действий не нужен.

### Routes

`routes.ts` содержит URL, HTTP-методы, схемы request/response, авторизацию и подключение hooks/handlers. Не выполняет запросы к БД и не реализует сценарии.

Обработчики регистрируются именованными функциями. Для извлечённых handlers задаются явные `Params`, `Body` и `Querystring` через generic маршрута; эти же типы используются в `FastifyRequest` обработчика. Это сохраняет связь схемы с типами при наличии hooks.

Проверки исходного значения, которое AJV может преобразовать, выполняются в `preValidation`. В categories этот hook отклоняет некорректный `iconKey`, включая пустую строку, до возможного приведения к `null`.

### Handlers

Каждый handler отвечает за один сценарий: получает данные запроса и авторизованного пользователя, проверяет правила, вызывает repositories/helpers и выбирает HTTP-ответ.

Handler может пользоваться Fastify `request`, `reply` и внедрёнными зависимостями через `this: FastifyApp`. Прямых вызовов `this.prisma.<model>.*` в новом handler быть не должно: зависимость передаётся в repository.

Например, переименование категории включает проверку непустого обновления, поиск исходной категории и дубликата, сохранение и выбор между успешным ответом, `404` и `409`. Нормализация имени и сериализация остаются отдельными чистыми функциями.

Общие HTTP-ошибки одного домена находятся рядом с handlers. Repository не получает `reply` и не определяет HTTP-коды. Дополнительный слой сценариев выделяется, когда правила действительно нужны нескольким обработчикам или другому способу запуска; для простых сценариев отдельный service-класс не требуется.

### Repositories

Repository содержит запросы Prisma, условия выборки, работу с ограничениями хранения и преобразование специфичных ошибок ORM в известные результаты операции.

Зависимость `PrismaClient` передаётся явно первым аргументом. Остальные аргументы описывают данные задачи: ID текущего счёта, категории, пользователя, тип, диапазон дат или изменения. `FastifyApp`, `request` и `reply` в repository не передаются.

Публичные параметры и результаты описываются типами приложения из `types/` либо локальным типом результата операции. Prisma-модели и типы её запросов используются внутри реализации repository. В categories `updateActiveCategory` возвращает `updated`, `not-found` или `conflict`; handler преобразует этот результат в HTTP-ответ.

Запросы, выполняемые независимо, можно объединять в `Promise.all`. Связанные изменения, которым нужна атомарность, выполняются транзакцией. Не заменять несколько запросов одной транзакцией автоматически при переносе кода: сначала определить требуемую согласованность сценария.

Такое разделение локализует смену ORM в repositories и инфраструктуре подключения. Само по себе оно не отменяет необходимость адаптировать DI и представление данных при миграции.

### Helpers

Чистая функция получает данные аргументами и возвращает результат. Она не обращается к Fastify, Prisma или глобальному состоянию запроса.

Примеры categories:

- `normalizeCategoryName` определяет нормализованное имя.
- `isCategoryIconKey` проверяет неизвестное значение по допустимым ключам.
- `serializeCategory` проверяет сохранённый тип операции и формирует контрактный ответ; неизвестный сохранённый ключ иконки превращает в `null`.
- `orderCategoriesByUsage` сортирует готовые категории и частоты. Получение статистики из БД остаётся в repository, выбор 90-дневного периода — в сценарии списка.

## Типы и HTTP-контракты

Источник HTTP-контрактов — [packages/api-contracts/typespec](../../../packages/api-contracts/typespec/main.tsp). Сгенерированные схемы подключаются через `#s/*`, а типы выводятся через `FromSchema`:

```ts
import type { FromSchema } from 'json-schema-to-ts';

import type CategorySchema from '#s/Category.js';

export type Category = FromSchema<typeof CategorySchema>;
```

Связанные типы выводятся из исходного: `Pick<Category, 'id' | 'name'>`, `Category['id']`, `NonNullable<Category['iconKey']>`. Общие типы не импортируются из handler, чтобы обработчики и repositories не зависели друг от друга по кругу.

Контрактный `Category` описывает уже проверенный ответ. Сохранённая запись может содержать более широкие `string` для `type` и `iconKey`. Для неё есть отдельный `StoredCategory`, использующий общие поля из Category. Преобразование выполняет сериализатор с проверками значений; assertion не заменяет эту проверку.

Для схем query, которые описаны локально, тип выводится из той же константы через `FromSchema`. Схема и TypeSpec-контракт должны описывать одинаковое поведение. Generated-файлы вручную не редактируются.

Aliases сервера:

- `#src/*` — исходники сервера.
- `#s/*` — TypeSpec JSON-схемы в TypeScript.
- `#generated/*` — generated-артефакты, включая Prisma Client.

В относительных ESM-импортах серверного кода используется расширение `.js`, соответствующее результату сборки.

## Доступ к данным и инварианты

Авторизация выполняется через `app.authenticate`: токен удостоверяет только пользователя и сессию. Счёт-зависимые маршруты лежат под `/accounts/:accountId/...`; общий preHandler `app.requireAccountAccess` проверяет доступ пользователя к счёту (владение или членство `AccountUser`, иначе 403), после чего handler берёт `accountId` из path и `userId` из авторизационного контекста и явно передаёт их в repository. ID записи из URL сам по себе не даёт права доступа: запрос также ограничивается счётом из path.

Активные категории выбираются с `deletedAt: null`. При удалении категория помечается датой, а существующие операции сохраняют связь с ней. Выбор активных категорий и историческая аналитика имеют разные требования к этому фильтру.

Частота категорий считается внутри текущих счёта и пользователя, по типу операции и включённому интервалу последних 90 суток. Repository выполняет один `groupBy`; handler не загружает все операции для подсчёта в памяти. Порядок: количество операций по убыванию, русское название, ID. Запрос без `sort=usage` не получает эту сортировку автоматически.

Нормализация имени и уникальность согласованы со схемой и миграциями. Для активных категорий уникальность внутри счёта и типа защищает частичный SQL-индекс. Предварительный поиск дубликата не заменяет ограничение БД: при конкурентном переименовании repository преобразует `P2002` в `conflict`, а handler отвечает `409`.

При структурном рефакторинге сохраняются существующие HTTP-коды, тексты ошибок, правила валидации и поведение гонок. Исправления поведения согласуются отдельно; известные ограничения записываются в проектный backlog.

## Тестирование и изменения

Новые и изменяемые unit/integration-тесты приложения размещаются по [правилу AGENTS.md](../../../AGENTS.md#код-и-проверка) в локальной `tests/` рядом с проверяемым кодом: маршрутные тесты — в `categories/tests/`, тесты helper — в `helpers/tests/`. Дерево выше показывает целевую структуру. Существующий `categories/test/` и тесты непосредственно рядом с исходниками остаются legacy-размещением до правки соответствующего теста; массовый перенос не требуется. При переносе обновляются импорты и остальные зависимые пути. Имена файлов сохраняют суффикс `.test.ts`, по которому Vitest находит их автоматически.

Главная проверка сценария — запрос через реальный Fastify-маршрут. Интеграционные тесты categories создают временную SQLite и применяют миграции. Это проверяет авторизацию, SQL-ограничения, сериализацию и взаимодействие модулей, включая конкурентный PATCH. Development-база в тестах не используется.

Чистые функции проверяются отдельно, если у них есть самостоятельные правила и значимые крайние случаи. Проверки копии реализации и обязательный тест на каждый перенос файла не нужны. Существующие корректные тесты при рефакторинге сохраняются; меняются только необходимые подключения.

Backend-проверки запускаются из корня:

```bash
pnpm --filter @budget/server build
pnpm --filter @budget/server lint
pnpm --filter @budget/server test
```

При изменении контрактов сначала обновляется TypeSpec и запускаются генераторы из [development guide](../../../docs/development.md#typespec-and-api-generation). После изменения Prisma-схемы нужны миграция и `prisma:generate`.

Если перенос entry point затрагивает [E2E server helper](../../frontend/e2e/support/isolated-backend-server.mts), обновляются его импорт и frontend typecheck/lint:

```bash
pnpm --filter @budget/frontend ts:check
pnpm --filter @budget/frontend lint
pnpm --filter @budget/frontend e2e --workers=1 --retries=0
```

Для изменения categories сохраняются сценарии иконок, переименования и личного порядка: доходы и расходы, мобильное разрешение, светлая и тёмная темы. Изоляция базы и аккаунтов должна работать и при последовательном запуске одним worker.
